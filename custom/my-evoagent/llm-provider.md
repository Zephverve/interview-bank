**题目**：多 LLM Provider 抽象层怎么做的？容灾切换怎么实现？

### 回答

- **MixinSession 设计**：不同 Provider 的 Session 用 Mixin 组合，把"通用逻辑"（消息管理、重试、流式解析）和"Provider 特有逻辑"（请求格式、工具调用格式、缓存标记）分离。加新 Provider 只需实现特有几个方法。
- **容灾切换**：主 Provider 调用失败（超时 / 限流 / 报错）时，自动切换到备用 Provider 重放当前请求。关键点是**消息格式要能无损转换**——Anthropic 和 OpenAI 的 tool call 结构不同，需要做规范化中间表示。
- **Prompt Cache**：Anthropic 的 cache 是显式标记的，需要把稳定部分（system prompt、长文档）放在前缀并打标记，变化部分放后面。收益是这部分 Token 成本降一个数量级，延迟也明显下降。**注意缓存有 TTL，且前缀一变就失效**。

**追问预判**：
- 「切换 Provider 会不会导致上下文不一致？」→ 会，尤其是不同模型的工具调用格式和终止符不同。所以切换前要做**格式归一化**，切换后最好重新注入一次系统指令。
- 「容灾重试会不会重复执行工具？」→ 这是个大坑。**只对幂等的 LLM 调用重试，工具执行结果如果已产生要用缓存复用，不能重放**。

**补充**：

**为什么需要**：生产环境不能依赖单一供应商。API 会限流、会抖动、会临时不可用。多 Provider 抽象是一层容灾保障，也是成本优化的基础（不同供应商不同任务价格不同）。

**最大的两个坑**：

**工具调用格式不统一**。Anthropic 和 OpenAI 的 tool call 结构不一样 —— 参数怎么序列化、工具结果怎么回填、多工具并行调用怎么表达，都有差异。所以切换前要做**格式归一化**，中间表示要能双向无损转换。我在 MixinSession 里做的就是这件事。

**幂等性问题**。这是更危险的坑：**如果 LLM 调用超时后重试，而这次调用其实已经触发了工具执行，重试会导致工具被执行两次**。所以我的原则是**只对幂等的 LLM 调用重试；已经产生结果的工具调用必须复用缓存，绝不重放**。
