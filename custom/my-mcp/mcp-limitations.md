**题目**：MCP 有什么局限？如果你要接入 10 个外部工具，用 MCP 还是直接写 Function Call？

### 回答

- **MCP 的局限**（要说得出，说明你不是无脑吹）：
  1. **上下文占用**：所有 Server 的工具 schema 都要注入模型上下文，Server 一多 token 膨胀严重。官方建议用**渐进式工具发现**缓解。
  2. **认证机制仍在演进**：多租户/无状态场景还在完善。
  3. **协议层无法强制安全**。
  4. **本地 stdio 场景的收益有限** —— 如果只是自己一个项目接几个工具，MCP 反而增加了一层进程通信开销。

- **决策框架**：
  | 场景 | 选择 | 理由 |
  |---|---|---|
  | 单人项目、工具少（<5）、无复用需求 | **直接写 Function Call** | MCP 的收益（跨应用复用）用不上，徒增复杂度 |
  | 团队多个应用共享同一批工具 | **MCP** | 一次实现，多端复用，这才是 MCP 的价值点 |
  | 工具需要独立部署、独立升级、独立鉴权 | **MCP** | 解耦部署 |
  | 对延迟极敏感、工具是纯本地逻辑 | **直接写** | 多一层进程通信是纯开销 |

- **一句话结论**：**"10 个工具不是判断标准，'要不要跨应用复用'才是"**。如果这 10 个工具只服务一个应用，我直接写；如果团队有 3 个 Agent 应用都要用这 10 个工具，那 MCP 一次性投入非常值。

**追问预判**：
- 「上下文占用具体怎么缓解？」→ 分层暴露（先给工具分类，按需加载）+ 描述精简 + 检索式工具选择（把工具描述向量化，按子任务召回 Top-K 再给模型）。
