**题目**：把四个记忆引擎用 Adapter 统一封装，这个抽象层怎么设计的？

### 回答

三段式分层。

1. **Adapter 层**：每个引擎一个 Adapter，把引擎原生接口翻译成**统一的能力接口**。统一抽象出的核心能力有四类：记忆写入、语义检索、知识图谱查询、数据导出。
2. **Router 层**：根据请求里的 `{engine}` 参数路由到对应 Adapter，同时负责**引擎的生命周期管理**（懒加载、连接复用、健康检查）。
3. **Config 层**：统一不同引擎的 LLM / Embedding 配置。这是最麻烦的部分——**不同引擎对 LLM 的调用方式完全不同**（Graphiti 在抽取实体时调用 LLM，LightRAG 在查询改写时调用，Mem0 在总结时调用），要统一注入同一套配置。

**追问预判**：
- 「不同引擎的能力不对等，怎么统一接口？」→ **我不做大而全的统一**。四个引擎的资源模型（graph / workspace / user / bank）本质不同，所以只定一个最小协议 `ensure_ready()`，统一收敛在**生命周期 + 错误语义 + HTTP 路由**三点，具体能力各自暴露。**如实承认欠缺**：更工程化的做法是加 capability 声明让上层运行时探测，`base.py` 里留了「第二阶段扩展」的注释，指的就是这个方向。
- 「这个抽象层最大的坑是什么？」→ **语义不对齐**。四个引擎对"记忆"的定义不一样：Mem0 存的是用户偏好类记忆，LightRAG 存的是文档知识，Graphiti 存的是实体关系的时序演化。统一封装解决了**接口层面**的一致性，但解决不了**语义层面**的不可比。所以我的评测部分才需要 LoCoMo/LongMemEval 这种统一基准来横评。
