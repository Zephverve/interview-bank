**题目**：LLM Judge 打出来的分你信吗？

### 回答

不能全信，我把它当**初筛工具**而不是**结论工具**。它有三个已知的系统性偏差：

**位置偏见** —— Judge 倾向于选先出现的那个选项，跟内容质量无关。我的缓解办法是把 A/B 顺序交换再测一遍，两次结论一致才算数。

**长度偏好** —— 长回答容易得高分，因为看起来"信息更丰富"。缓解办法是在评分 Prompt 里明确禁止因长度加分，并且把正确性、完整性、无幻觉拆成独立维度分别打分，而不是给一个总分。

**自我增强偏见** —— Judge 会给同族模型的输出更高分。缓解办法是换不同厂商的模型做 Judge，对比两份评分的一致性；如果差异很大，说明这个结论不可靠。

**说实话：人工抽检我这块没做。** 评测链是全自动的 —— token F1 / 精确匹配 / ROUGE 加 LLM 裁判，跑完直接出 JSON。三个月里我的重心放在引擎接入和评测流水线本身，人工验证这块没来得及做。**这是我事后回头看，觉得这段实习最大的欠缺。**

不过我对「Judge 不可信」这个问题的处理，集中在了**减少 Judge 调用次数 + 提高确定性**上，这也有实际价值：

**① 能用规则算的绝不用 LLM。** LoCoMo 的主指标就是纯规则的 token 级 F1（小写化 + 去标点 + 去冠词 + Porter 词干化），ROUGE 也是规则分。这些指标只需要人工标注的 gold，不需要模型判断，**确定、可复现、零成本**。LLM 裁判只用在「语义对不对」这种规则算不出来的地方。

**② 给 Judge 加短路逻辑**（`_judge_short_circuit`）。在明显对 / 明显错的情况下**直接返回分数，不调 LLM**：精确匹配命中 → 1.0；日期格式等价（2023-05-07 ↔ 7 May 2023）→ 1.0；Yes/No 极性一致 → 1.0，不一致 → 0.0。这既省了 token，也让结果**更稳定** —— 这些判断有确定性答案，交给 LLM 反而引入随机性。

**③ 把 Judge 的输出约束成五档离散分**（0 / 0.25 / 0.5 / 0.75 / 1），并且**空 gold 强制二元**（弃权 → 1，编造 → 0，不允许给部分分）。原因是连续分数在 LLM 裁判里极不稳定，同一份输入多次调用会飘；离散档位加 `temperature=0` 能把抖动压下来。

**所以我现在的原则是**：**跨引擎比较看相对排名，不看绝对分数**，因为绝对分数没有可比基准；同时用短路 + 离散分尽量降低 Judge 的不确定性。但**我清楚这不能替代人工抽检** —— 严格做法是随机抽样人工打标、算 Kappa 衡量人机一致率，一致率低就说明该改 Judge 的 Prompt 而不是数据。这一步我没做，是我该补的。
