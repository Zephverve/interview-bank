**题目**：Agentic RAG 和传统 RAG 的区别？成本怎么控制？

### 回答

- **区别**：传统 RAG 是**单次流水线**（检索→生成，一步到位）；Agentic RAG 是**带反馈的闭环**——有质量门控，不达标就重新检索或重写查询，本质是把"检索"变成可以被 LLM 自主决策和迭代的过程。
- **你的实现**：LangGraph 多节点闭环（意图路由 → 查询改写 → HyDE → 混合检索 → **质量门控** → 上下文压缩 → 生成 → **Faithfulness Guard**），门控和校验是两个反馈点。
- **成本问题**（这是 Agentic RAG 的固有代价）：
  1. **节点多 → 延迟高**：解耦成 8 个节点，如果每个都调 LLM，延迟可达秒级甚至十秒级。
  2. **重试 → 成本不可控**：质量不达标就重检索，最坏情况成本翻几倍。
  - **控制手段**：
    1. **意图路由前置分流**：简单事实型问题走**快速通道**（跳过 HyDE 和重写，直接混合检索+生成），只有复杂问题走完整链路。**大部分查询是简单的**，这一步就砍掉了大头成本。
    2. **限制重试次数**：最多重检索 1 次，重生成 1 次，然后降级返回。
    3. **门控用轻量模型**：质量门控不需要 14B 大模型，用小模型或规则（召回分数阈值）判定即可。
    4. **缓存**：相同/相似 query 的检索结果缓存复用。

**追问预判**：
- 「Query Rewrite 算不算 Agentic？」→ **边界比较模糊**。我的判断标准是**有没有"基于中间结果的决策"**：固定执行一次改写不算 Agentic（那是流水线的一步）；根据改写后的检索结果**决定是否再改写、要不要换检索策略**，这才算。核心是**控制流由模型的判断驱动**，而不是写死的顺序。
