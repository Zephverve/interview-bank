**题目**：这个项目遇到过的失败案例？

### 回答

**案例：跨论文信息混淆。**（这是你项目里最真实、最有价值的一个案例，一定要讲好）

**现象**：
"大概做到 RAG pipeline 第二个迭代的时候，我发现 LLM 经常把不同论文的信息混在一起。用户问'A 论文用了什么激活函数'，检索返回了 A 和 B 两篇论文的片段，LLM 有时候会把 B 论文的内容安到 A 论文头上。**这个问题很隐蔽 —— 单独看回答内容是对的，只是引用错了。**"

**定位过程**：
"最初我在 prompt 里加'请基于提供的论文回答'，没用，LLM 还是会混淆。这说明不是 Prompt 措辞问题，是**机制层面缺了核对环节**。所以我在 LangGraph 里加了 **Faithfulness Guard** 节点：生成后逐条核对引用是否能在父块原文中找到支撑。"

**根因**：
"根因是**生成和验证之间没有闭环**。模型生成时会把参数化知识和检索内容混在一起，而没有任何环节去检查'这句话的依据到底在不在给定材料里'。"

**修法**（两层）：
1. **Faithfulness Guard 节点** —— 用正则抽出答案里的引用，检查对应的 chunk 是否在命中列表里，再对引用句和 chunk 做 embedding 余弦相似度比对（阈值 0.42）。无引用且回答过长 → 判定不通过。
2. **Self-RAG 分支** —— Guard 失败后判断是"检索不够"还是"生成胡说"：前者走 re-retrieve（换 query 或加 HyDE），后者只重生成。

**效果**：
"早期单节点校验通过率大约 **72% → 86%**。配合 MinerU 改善 PDF 解析后，引用可追溯性明显提升。现在整条 Agentic 链路端到端更稳，但**表格/公式类问题仍有边界 case**。"

**收尾金句**：
"这个案例让我确认了一件事：**检索质量是生成质量的上界**。你不可能靠 Prompt 让模型从一个错误的上下文里答出正确的引用。"

**为什么这个案例好**：它有隐蔽性（回答内容对、只是引用错）、有排查过程（先试 Prompt 失败）、有机制性根因（缺闭环）、有量化效果（72%→86%），最后还留了边界（表格公式仍有问题）。**这是一个完整可信的工程案例。**
